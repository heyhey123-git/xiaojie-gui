# 拖拽到底是怎么工作的

[English](dragging.md) | 简体中文

玩家按住左键在几个格子上一划，看起来只是一个动作。但在协议里它是**一串包**，而且这串包在
服务端会被拆成三种完全不同的结局。知道这件事，你才能写出"商品格不能被拖走""付款格拖进来也算付款"
这种菜单；不知道它，就会出现"玩家拖了一下，脚本什么都没收到"。

这一页讲清楚三件事：拖拽在底层是什么、它到脚本这一层变成了什么、以及为什么我们把它做成了现在这样。

## 你只需要记住的结论

1. **一次拖拽 = 一次交互**。`on menu interact` 只跑一次，`the dragged slots` 是被扫过的所有格子。
2. **`the click type` 还是 `left/right/middle mouse button`**，拖拽不会变成一个新的点击类型。
3. **`cancel event` 是全有或全无**：点一下＝这一格不动；拖拽＝整次拖拽都不生效（协议上也只能这样）。
4. **拖拽只会"放"，永远不会"拿"**。所以记账时：谁拿了什么 → 只看点击；谁放了什么 → 看拖拽。

## 底层：相位藏在按钮里

客户端拖拽时发的不是"拖拽包"，而是一串普通的容器点击包（`clickType = QUICK_CRAFT`）。协议里没有
多余字段了，于是相位被编进了 **button**：

| 相位 | 左键 | 右键 | 中键（创造） |
|---|---|---|---|
| 开始 | `0` | `4` | `8` |
| 继续 | `1` | `5` | `9` |
| 结束 | `2` | `6` | `10` |

低 2 位是相位（开始/继续/结束），高位是"用哪个键拖的"。vanilla 给三种键起的名字正好说明了它们的语义：

- 左键 = `CHARITABLE`：把光标上的那叠**均分**给扫过的格子；
- 右键 = `GREEDY`：每个格子**只放 1 个**；
- 中键 = `CLONE`：每个格子放**一整叠**（创造模式限定）。

**开始包带的槽位会被忽略**：服务端只在"继续"包里收集格子，一个继续包一个格子。

## 服务端的三个结局

收到"结束"包时，服务端按收集到的格子数分三种：

| 收集到的格子 | 服务端做什么 | 插件/脚本看到什么 |
|---|---|---|
| **0 格** | 什么都不做 | **没有事件** |
| **恰好 1 格** | 把它**改写成一次普通点击** | 一次普通点击：`the clicked slot` 是那一格，`the dragged slots` 没有值 |
| **≥2 格** | 一次性应用，并发**一次** `InventoryDragEvent` | 一次交互：`the dragged slots` 是被扫过的格子 |

另外两条规则决定了"什么算一格"：

- 光标是**空**的时候拖拽：直接清状态，什么都不发生（零事件）。
- 每个格子要被收进集合，必须**放得下**光标上的东西，而且光标里的数量**还够分**（`数量 <= 已收集格数`
  就跳过）。所以 **1 件物品最多只能扫到 1 格**，2 件最多 2 格；把一个石头拖过 3 个空石头的格子，
  也只有一格会被收进去。

### 为什么"拖拽只能放，不能拿"

结束包做的是：把光标上那叠按规则分给每个被扫过的格子，然后从光标里减掉。**没有任何一个相位是
"把格子里的东西拿到光标上"**。所以：

- 想拿走东西，只有点击这条路（普通点击、Shift 点击、数字键、双击收集、Q、副手交换）——全都会作为
  点击到达脚本；
- 拖拽只能**放入**。这对商店/背包的记账是个好消息：**谁拿了什么，只需要处理点击。**

## 脚本这一层

```skript
on menu interact:
    # 一次交互只跑一次，不管是点一下还是拖过十格。
    set {_type} to the click type            # left / right / middle mouse button
    set {_slots::*} to the dragged slots     # 点一下：没有值；拖拽：被扫过的所有格子
    set {_held} to the cursor item           # 玩家手里拿着的东西（拖拽时就是要铺出去的那叠）

    # 商品格（0、1）和预留格（5）不许动：碰到就整次拒绝
    if {_slots::*} is not set:
        set {_slots::*} to the clicked slot
    loop {_slots::*}:
        if loop-value is 0 or 1 or 5:
            cancel event
            stop

    # 自由格：拖进来也算"放进来了"，这里按格结算
    loop {_slots::*}:
        if loop-value is 11 or 12 or 13:
            settle(player, {_held}, loop-value)
```

几个要点：

- **`the clicked slot` 是"第一个"被碰到的格子**（拖拽时），`the dragged slots` 才是全部。只关心某一格
  的代码写 `the dragged slots` 更好。
- **`and when clicked` 的格子回调也会被拖拽触发**，每格一次，而且回调看到的事件里 `the clicked slot`
  就是它自己那一格。也就是说：为点击写的格子回调，玩家改成拖过这一格时照样工作。
- **`the cursor item` 只在 `static` 模式下有值**。幽灵模式的窗口是服务端自己画的，没有真实的"手上那叠"。
- **槽位号是"窗口槽位"**：`0` 是容器左上角，容器之后接着玩家背包的 27 格和快捷栏 9 格，两种模式口径
  一致。`static` 模式下玩家背包那一半不属于菜单（那里是玩家自己的东西），所以对它写图标没有意义。

## 实测：同一个手势，四种结果

下面这些是在真服务端 + 真客户端上跑出来的（客户端直接发原始包，因为 mineflayer 不会模拟拖拽）：

| 手势 | 服务端收集 | 事件 | 结果 |
|---|---|---|---|
| 左键点一下 | —— | 一次 `InventoryClickEvent` | 物品移动 |
| 拿 **1 件**物品扫过 2 格 | 1 格 | 一次 `InventoryClickEvent` | 和点一下**完全一样**（落在第一格） |
| 拿 **2 件**物品扫过 2 格 | 2 格 | **只有**一次 `InventoryDragEvent` | 每格 1 件 |
| 空光标拖拽 / 开始包直接接结束包 | 0 格 | **没有任何事件** | 什么都没发生 |
| 拖过"放不下"的格子（例如往绿宝石上拖石头） | 跳过该格 | 看剩下几格 | 那个格子纹丝不动 |

最后一行是很容易踩的坑：**你以为拖了 2 格，服务端可能只收了 1 格**，于是它又变成了一次点击。

## 这些是怎么查出来的

不是猜的，三个来源互相印证：

1. **协议**：`mineflayer` 自己的窗口同步用的就是 `mode: 5, mouseButton: 2`，注释写着
   *"end of a drag that never started"*；
2. **NMS 字节码**：`AbstractContainerMenu.doClick` 里 `getQuickcraftHeader` / `getQuickcraftType` 取的正是
   那两段位，`getQuickCraftPlaceCount` 就是上文的均分公式；整个服务端 jar 里**只有**这个类引用
   `InventoryDragEvent`；
3. **CraftBukkit 的上层**：点击包处理器在 `QUICK_CRAFT` 分支直接跳过构造 `InventoryClickEvent` 的那段
   代码——这就是"多格拖拽没有点击事件"的原因；而"恰好 1 格"那种会被重新合成成一次点击。

对应的自动化：

- `src/test/.../gui/interact/QuickCraftTest.kt`：9 个按钮的相位/键/点击类型解析；
- `src/test/.../gui/receptacle/DragHandlingTest.kt`：一次拖拽 → 一次交互（含格子列表）、单格拖拽 → 点击、
  空拖拽 → 零事件、取消 → 取消整个拖拽事件；
- `server-test/skript/12-client-drag.sk` + `server-test/client/bot.mjs`：**真客户端发原始拖拽包**，验证
  "拒绝的拖拽一个格子都不动"和"接受的拖拽每格都填上"。
