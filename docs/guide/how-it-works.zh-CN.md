# 窗口如何工作

[English](how-it-works.md) | 简体中文

玩家输入 `/shop`，菜单出现，点击按钮后执行脚本。这背后有四个环节：**菜单定义**、**每个玩家独立的窗口**、
**窗口与客户端的同步方式**，以及**点击进入 Skript 前的判定**。顺着一次点击的来龙去脉看下去，许多看似意外的行为就有了解释。

这一页从底层机制讲起，再说明它们如何影响脚本。一次有效的多格拖拽只触发**一次交互**；这里只介绍与点击相关的部分，
完整说明见[拖拽如何处理](dragging.zh-CN.md)。

## 你只需要记住的结论

1. **菜单是定义，窗口是某个玩家手里的那一份副本。** 同一个菜单可以供多人同时查看，每个人的页码和图标都可以不同。
2. **两种模式在协议上是两回事**：`phantom` 通过数据包呈现窗口，`static` 使用服务端真实创建的物品栏。这决定了物品由谁管理。
3. **窗口显示主要靠三种发包操作**：发送整个窗口、更新某一格、重新打开窗口。修改标题采用最后一种，因为协议没有单独的“设置标题”包。

<a id="菜单是定义窗口是某个玩家手里的那一份副本"></a>

## 菜单与窗口

底层用三个对象区分共享定义与玩家各自的状态：

- `Menu` 保存定义：页面（布局与标题）、图标映射、点击回调、冷却，以及当前观看者。它本身不保存窗口的标题和内容。
- `ViewReceptacle` 表示**一个窗口**，包含标题、布局、内容数组和观看者。玩家打开菜单时创建，关闭时释放。
- `MenuSession` 记录某个玩家当前的 `menu`、`page` 和 `receptacle`。

执行 `open menu` 时，插件先触发 `on menu open`，再为目标页创建窗口，装入页面内容并发送给玩家。
两个人打开同一个菜单，得到的是两个独立窗口，只是它们来自同一份定义。

在脚本中，这意味着：

- `the menu window of player` 表示玩家的窗口；没有打开窗口时，表达式**没有值**。事件中的 `the event-menu window` 表示本次事件所在的窗口。
- 对窗口的修改只影响**那个玩家**。例如 `set icon in slot 5 of {_window}` 和
  `update title of the menu window of player to …`；后者需加 `and refresh` 才会立即更新显示。
- 对**页面**的修改是共享的。`override slot` 和 `map key` 修改页面定义，影响正在查看该页的所有玩家；在 `phantom` 下，加上 `and refresh` 才会立即更新显示。
- 窗口单独设置的图标不属于菜单定义。之后翻页或执行 `override slot`、`map key` 时，页面仍会向自己管理的格子写入内容，覆盖窗口中原有的图标。

```skript
on menu interact:
    # 页面：正在看第 1 页的所有人都会变
    override slot 5 in page 1 to diamond for {_menu}
    # 窗口：只有点它的那个玩家会变
    set icon in slot 5 of the menu window of player to diamond
```

脚本中称它为**窗口**；注册的类型名仍是 `menusession`，因此也可以写 `session`，两种写法指向同一个对象。
需要只修改某个玩家的显示时，才需要指定窗口。各语法的适用范围见[窗口](windows.zh-CN.md)中的对照表。

<a id="两种模式在协议上是两回事"></a>

## 两种模式的区别

`phantom` 和 `static` 使用不同的机制，不只是显示风格不同。

**`phantom`：由插件通过数据包呈现窗口。** 插件分配窗口编号，先发送打开界面包，再发送整窗内容。
此后，玩家发来的**每一个容器点击包都会被取消**，插件再重发相应内容。服务端没有对应的真实物品栏，
物品只保存在插件的内容数组中。玩家无法取走它们；看似拿起物品的瞬间只是客户端预测，随后会被数据包纠正。

**`static`：使用真实物品栏。** 插件为玩家打开 Bukkit 物品栏，监听 `InventoryClickEvent`、
`InventoryDragEvent` 和 `InventoryCloseEvent`。其中的物品可以移动、交换或丢弃；没有额外保护时，
用 `override slot` 放入的图标也能被拿走。

两点区别会直接影响脚本：

- **玩家背包区域的归属。** `static` 下，窗口下方的 36 格始终是玩家自己的背包，不属于菜单；`setElement`
  会拒绝写入容器范围外的格子并给出说明。`phantom` 下，背包显示时会实时映射玩家携带的物品；隐藏后，这片区域才交给菜单使用，由 `player layout` 描述布局。
- **刷新与光标物品。** `static` 由服务端物品栏保持同步，`refresh the menu window …` 不执行任何操作。
  `the cursor item` 也只有在 `static` 下有值，因为 `phantom` 的点击包不携带物品本身。

可以把 **`phantom` 理解为按钮面板，把 `static` 理解为真实箱子**。完整对照与各项开关见[两种模式](modes.zh-CN.md)。

## 窗口是怎么画出来的，以及 `refresh` 为什么存在

打开窗口时，数据包的顺序固定：先发送**打开界面包**，包含窗口编号、布局对应的窗口类型和标题；
再发送**整窗内容包**，按槽位顺序列出各格的物品或空值。

内容来自当前页面：先按布局将映射图标放入对应格子，再应用 `override slot` 的覆盖内容。
内容数组的长度与客户端窗口一致，容器格子在前，玩家背包区域在后。在 `phantom` 下，背包显示时填入玩家的真实物品，隐藏时则供菜单使用。

**物品为什么会“弹回去”？** 客户端会在收到服务端响应前，先预测容器操作的结果。`phantom` 没有真实物品栏负责同步，
因此插件会取消点击包，再重发受影响的内容：

- 只影响当前格子的点击：重发该格。
- 可能在格子之间移动物品的操作，如 Shift 点击、数字键、副手交换、中键和双击收集：重发整个窗口。
- 拖拽：重发经过的每一格，仅恢复一格并不足够。

这就是物品“拿起后又弹回”的原因，也是 `phantom` 比 `static` 多一些性能开销的地方。
纠正在**检查点击冷却之前**完成，因此即使本次点击随后因冷却而被忽略，客户端显示也已恢复。

**`refresh` 用于主动同步显示。** `refresh the menu window …` 重发整个窗口，`refresh the slot N in …` 只重发一格。
在 `static` 下，两者都不执行操作，因为真实物品栏会自行同步。
`set icon in slot N of {_window}` 调用 `setIcons(…, true)`，本身就会发送窗口内容，无需另写 `refresh`。

## 为什么改标题要重新开一次窗口

**协议没有单独的“设置标题”包。** 要改变客户端窗口的标题，需要再次发送打开窗口的包：

- `phantom` 先重发打开界面包，再发送全部内容。操作通过 `TaskUtil.sync(delay = 0)` 延后到**下一个 tick**，
  避免客户端忽略窗口刚打开那一 tick 内的标题变化。
- `static` 先设置真实容器菜单的标题，再发送新的打开界面包，在**同一个 tick** 内完成。

`phantom` 的这一 tick 延迟用于适配客户端行为，不是对网络延迟的估算。由此有三个需要留意的细节：

- **改标题也会重发内容。** 打开界面包之后会发送完整内容，客户端按窗口此刻的内容数组恢复显示。
- **关闭窗口后，延迟的标题更新不会重新打开它。** 更新任务会重新检查观看者；关闭窗口时已清除观看者，因此任务不再执行。客户端测试覆盖了这一顺序。
- **屏幕显示可能比内部状态晚一 tick。** `the title of {_window}` 读取窗口对象的标题，语句执行后就能读到新值；
  客户端则要等新的打开界面包到达才更新。人工验收中“一条命令里开窗并改标题”检查的就是这种情况。

语法（`and refresh`、每页标题）见[窗口](windows.zh-CN.md)，文本与颜色写法见[标题](titles.zh-CN.md)。

## 一次点击是怎么被判定的

两种模式的点击来源不同，但都会在交给脚本之前完成分类：

- **`phantom`**：插件在网络线程读取容器点击包，根据其中的*模式*、*按钮*和*槽位*判断点击类型，再交回主线程。
  无法识别的点击会被**忽略**，不会抛出异常；这个窗口由插件管理，不会交给服务端的真实物品栏处理。
- **`static`**：由 Bukkit 的 `InventoryClickEvent` 提供点击类型，拖拽则来自 `InventoryDragEvent`。
  槽位使用**原始槽位编号**，而不是 `getSlot()`。后者相对于被点击的物品栏编号，如果将背包中的编号误当作窗口编号，就可能触发错误容器格子的回调。

接下来的处理顺序固定：

1. **`phantom` 先纠正客户端预测。** 即使交互随后被拒绝，这一步也会执行；`static` 不需要这一步。
2. **检查点击冷却。** 距玩家上一次被接受的点击不足 `click delay` 时，整次交互会被**静默忽略**：不触发事件或格子回调，也没有提示。
   默认冷却为 `create menu` **50 毫秒**、`build a menu` **5 毫秒**。
3. **执行格子回调。** 本次交互涉及的每一格各执行一次，拖拽则是经过的每一格。
4. **触发 `on menu interact`。** 此时 `cancel event` 可以拒绝交互，但无法撤销已经执行的回调。
5. **应用 `locked icons`。** 因此 `static` 菜单中的购买回调仍能触发，而商品不会被拿走；`phantom` 的物品本来就无法移动。

`the click type` 使用 **Skript 自身的点击类型**与字面量，例如 `left mouse button`、`number key`、`drop key` 和 `swap offhand key`。
`the event-clicktype` 返回同一个值。由于九个数字键都归为 `number key`，具体按键需通过 `the pressed number key` 读取：
数字键点击时返回 1 到 9，其余点击没有值。

`cancel event` 拒绝的是**整次交互**：`static` 会取消 Bukkit 事件，阻止物品移动；`phantom` 本就不允许移动，客户端显示由前面的纠正操作恢复。
它**不能撤销已经执行的格子回调**。要提前终止回调，请在回调内部使用 `stop`。

**一次拖拽就是一次交互。** 在 `phantom` 下，拖拽由一串点击包组成，阶段信息编码在按钮字段中；插件收集这些包，
在结束时一次性报告结果。经过的格子都列在 `the dragged slots` 中。仅涉及一格的拖拽会被游戏按普通点击处理。
完整机制、三种结果与脚本写法见[拖拽如何处理](dragging.zh-CN.md)。

## 所有菜单操作都必须在主线程上

菜单操作涉及服务端物品栏与窗口，必须在服务端主线程执行。异步 `execute` 中再调用 `run task later`、
其他插件的异步回调，以及声明为 `on … async` 的自定义事件，都可能让操作落在错误的线程上。

插件在**实际执行时**检查线程，而不是在解析语法时检查。不在主线程上的调用会被**放弃**，并输出对应操作的说明。
打开、关闭、翻页、改标题、刷新、设置列表和写入窗口图标都有各自的提示，例如：
`Menu can only be opened from the main server thread, …`。

这项检查**无法关闭**，因为异步调用不受支持。插件本身也没有配置文件；启动横幅的颜色由控制台能力
（`net.kyori.ansi.colorLevel`）决定。更多限制见[尚未支持](not-supported-yet.zh-CN.md)。

## 哪些格子属于谁

槽位采用**窗口编号**：`0` 是容器左上角，后面紧接玩家的 27 格主背包和 9 格快捷栏。两种模式使用相同的编号方式。
背包区域的起点根据容器范围推算，并非每个布局单独指定；容器范围若少算一格，背包槽位就会整体偏移一格，而不一定报错。
唯一的例外是 lectern：客户端菜单只有一格，没有玩家背包区域，因此它的布局与内容包也只有一格。

容器中，页面管理的格子包括布局中映射了图标的格子，以及通过 `override slot` 写入的格子。
在 `static` 下，`with locked icons` 保护的就是这个集合：点击、Shift 点击、数字键、副手交换、丢弃和双击收集都不能取出或放入物品；
拖拽只要经过其中一格，整次操作就会被拒绝。`phantom` 本就不允许移动物品，因此这个开关没有额外作用。
布局中的**空格子**仍可自由使用，同一个菜单因此既能保留固定按钮，也能留出存放物品的空间。

下方背包区域由模式和 `hide player inventory` 决定：

| | 容器下方那 36 格 |
|---|---|
| `phantom`，背包显示 | 实时映射玩家自己的物品 |
| `phantom`，背包隐藏 | 供菜单使用；用 `player layout` 定义布局，用 `set icon in slot N of {_window}` 放入图标，点击时照常触发交互 |
| `static` | 始终是玩家的真实背包，不属于菜单；设置 `player layout` 只会产生警告，不会改变内容 |

背包显示时，页面为该区域设置的图标会在**发送窗口之前清除**，不会出现在玩家恰好空着的背包格子里。
`set icon in slot N of {_window}` 则只修改该玩家的窗口，不属于页面定义，也**不受 `locked icons` 保护**，可用于为不同玩家显示各自的高亮。

`player layout` 的写法见[页面](pages.zh-CN.md#player-layout)，如何向格子写入图标见[填充菜单](filling-menus.zh-CN.md)。

## 翻页发出去了什么

翻页并非简单地重画整个窗口，而是依次完成以下操作：

1. **检查目标页布局。** 箱子行数不同或容器类型不同等不兼容布局，会在任何修改之前被拒绝，并给出提示；页码与内容保持不变。
   窗口布局不可变，翻页不能把物品迁移到形状不同的窗口。
2. **触发 `on page turn`。** 事件可以取消；其中的 `the title` 是目标页标题，修改只影响这一次翻页。
3. **只清除原页面管理的格子。** 包括已映射图标的布局格子和 `override slot` 覆盖过的格子，其余内容保持不变。
   因此，玩家放在空格子中的物品可以跨页保留。
4. **装入目标页。** 应用图标、槽位覆盖与列表内容。
5. **按需更新标题。** 标题不同时，重发打开界面包及内容；标题相同时，只执行普通 `refresh`。
   两种情况的发包方式不同，`static` 也不必每次翻页都发送两遍完整窗口。

每页都有独立标题，翻页时通常也会更换标题。`turn to page 2 for player with new title "…"` 指定的标题
**仅用于本次显示**，不会写回页面。语法与页码规则见[页面](pages.zh-CN.md)。

## 窗口什么时候消失

| 发生了什么 | 底层意味着什么 |
|---|---|
| 玩家关闭窗口（ESC 或菜单里的关闭按钮） | `phantom` 收到关窗包，`static` 收到 Bukkit 关闭事件；两者都会通过关闭处理器触发 `on menu close`，再释放窗口 |
| `close the menu …` / `close the menu window …` | 插件主动发送关窗包，再释放窗口 |
| `destroy the menu …` | 关闭该菜单所有观看者的窗口；菜单本身也无法再打开或交互 |
| 玩家切换到另一个菜单 | 旧菜单触发一次 `on menu close`，该玩家从旧菜单的 `menu viewers` 中移除 |
| 玩家退出、死亡或切换世界 | 先触发 `on menu close`，此时仍可保存容器内容；随后释放窗口，并**清空** `static` 的真实物品栏，避免物品一直留在内存中直到关服 |
| 重载脚本（`/skript reload`） | **先销毁所有菜单**，再解析新脚本 |

尤其要留意脚本重载：菜单持有创建它的脚本中的回调。如果菜单在重载后继续存在，下一次点击就可能调用已经失效的代码。
因此插件在 Skript 预初始化事件中、解析新脚本之前销毁所有菜单，再由脚本重新创建。这也是通常把菜单写在 `on load:` 中的原因。
使用已有 id 创建菜单时，旧菜单也会被销毁，不会出现两个同 id 菜单并存的情况。

相关脚本语法与 `menu viewers` 的说明见[窗口](windows.zh-CN.md)。

## 这些是怎么查出来的

上述行为由单元测试、真实服务端测试和真实客户端测试验证；自动化无法确认的显示与操作细节，还需要人工验收。

**单元测试**覆盖无需启动服务端的逻辑：

- `ViewLayoutTest` 检查各布局的容器格子数是否符合 Bukkit 定义，并单独检查 lectern 的 **1** 格窗口与 beacon 的 **37** 格窗口。
- `PhantomReceptacleTest` 检查发包方式：打开时发送打开界面包和整窗内容包，改标题时再次发送打开界面包，关闭时发送关窗包。
  它还检查 lectern 的单格内容包，以及背包显示时是否清除页面在背包区域设置的图标。
- `ViewReceptacleTest` 检查关闭窗口会清除观看者，确保延迟的标题更新不会重新打开窗口。
- `MenuTest` 检查翻页是否保留非页面管理格子的内容、是否在修改前拒绝不兼容布局，以及 `destroyAll` 是否销毁所有菜单。
- `PageLockedIconsTest`、`PageAuditRegressionTest` 和 `CooldownTest` 覆盖点击规则：各种取出受保护图标的方式均被拒绝，
  涉及受保护格子的拖拽会整体取消，从玩家背包 Shift 点击仍可将物品送入空格子，一次回调只产生一个全局事件，冷却也会拒绝过早到来的点击。

**真实服务端测试**（`./gradlew serverTest`）启动 Paper 26.2、Skript 和 PacketEvents，验证语法元素能否注册、
脚本能否解析、行为脚本中的原版 `assert` 是否通过，以及日志是否符合预期：运行期消息使用正确通道，
没有 `Severe Error`，也不再出现已修复的解析错误。每个 `@Examples` 示例都会在这里解析，无法解析的示例会导致构建失败。

**真实客户端测试**（`./gradlew clientTest`）驱动 Minecraft 客户端，读取窗口标题、类型，以及已知格子中物品的类型和名称。
它检查翻页后的窗口、归页面所有的背包区域、lectern 的单格窗口、beacon 的 1 + 36 格、dropper 的三列九格布局、
bot 通过原始包发出的拖拽，以及同一 tick 内改标题后关闭的窗口不会重新出现。
测试使用 26.1 客户端，通过 ViaVersion + ViaBackwards 连接。因此它验证的是数据包能否经过真实协议转换层到达客户端，
不等同于原生 26.2 客户端验收。边界详见[尚未支持](not-supported-yet.zh-CN.md)。

**人工验收**（`docs/manual-acceptance.zh-CN.md`）使用真实 26.2 客户端，补充确认以下细节：

- **lectern 的单格窗口**（`/acctype lectern`）：是否显示对应方块的界面，以及槽位数错误时玩家背包是否整体偏移。
- **重新打开后的标题**（`/acc sametick`）：一条命令内打开窗口并改标题后，屏幕是否确实显示新标题，而不只是客户端读回了新值。
- **拖拽各阶段**（`/acc drag`）：客户端测试覆盖持有物品时的真实拖拽包；人工验收补充空光标操作、物品最终落点，以及被拒绝的拖拽是否留下异常显示。

文档也列出了自动化尚未覆盖的情况：只存在于客户端显示中的“幽灵物品”，以及两个客户端同时查看同一菜单的行为。
目前客户端测试只有一个 bot。
