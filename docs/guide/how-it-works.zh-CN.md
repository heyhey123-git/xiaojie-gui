# 窗口到底是怎么工作的

[English](how-it-works.md) | 简体中文

玩家输入 `/shop`，一个箱子出现，里面四个按钮，点一下就执行几行脚本。要做到这件事，底层有四个东西必须互相对上：
一份**谁也不会看到的定义**、每个玩家自己的**那一份副本**、一个"要么用包画出来、要么是真实物品栏"的窗口，
以及一次在 Skript 听说之前就已经判定完的点击。绝大多数"它为什么是这个表现"的问题，答案都是这四件事之一。

这一页一件一件地讲：插件在底层做了什么，因此脚本看到什么。拖拽是同一个故事的完整展开——不管扫过几格，
它都是**一次**交互——所以这里只用一小段带过，细节在[拖拽到底是怎么工作的](dragging.zh-CN.md)。

## 你只需要记住的结论

1. **菜单是定义，窗口是某个玩家手里的那一份副本。** 一个菜单可以同时给十个人看，各自在不同的页、有各自的图标。
2. **两种模式在协议上是两回事**：`phantom` 用包自己把窗口画出来，`static` 是服务端真实创建的物品栏。谁拥有物品由它决定。
3. **发出去的东西只有三种包**：整个窗口、某一格、以及"把窗口再打开一次"——最后这种就是"改标题"，因为协议里
   没有"设置标题"这个包。

## 菜单是定义，窗口是某个玩家手里的那一份副本

底层是三个对象，把它们分开正是"每个玩家自己的内容"能成立的原因：

- `Menu` 是定义：页面（一个页面 = 一份布局 + 一个标题）、图标映射、点击回调、冷却，以及现在有谁在看它。
  它自己没有标题，也没有内容。
- `ViewReceptacle` 是**一个窗口**：一个标题、一份布局、一个内容数组、一个观看者。玩家打开菜单时创建，关闭时丢掉。
- `MenuSession` 是"某个玩家的那一对东西"：他的 `menu`、他的 `page`、他的 `receptacle`。

`open menu` 做的就是复制一份：触发 `on menu open`，为要显示的那一页造一个窗口，把页面装进去，然后发出去。
所以两个人打开同一个菜单，拿到的是两个窗口，只不过它们是从同一份定义生成出来的。

脚本看到的：

- `the menu window of player` 就是他的窗口（没有窗口时**没有值**），事件里的 `the event-menu window` 就是这次事件发生所在的那个窗口。
- 写在窗口上的东西只属于**那个玩家**：`set icon in slot 5 of {_window}`、
  `update title of the menu window of player to …` 只改他一个人的窗口（后者要加 `and refresh` 才会立刻到屏幕上）。
- 写在**页面**上的东西是共享的：`override slot` 和 `map key` 会送到正在看那一页的所有人，因为它们改的是
  窗口据以生成的那一页。
- 窗口自己的图标不属于菜单：之后**页面**写下的东西——翻页、`override slot`、`map key`——会落在那一页拥有的格子上，
  盖掉这个玩家窗口里原来的内容。这就是"这个玩家的窗口"和"菜单"的全部区别。

```skript
on menu interact:
    # 页面：正在看第 1 页的所有人都会变
    override slot 5 in page 1 to diamond for {_menu}
    # 窗口：只有点它的那个玩家会变
    set icon in slot 5 of the menu window of player to diamond
```

面向脚本的词是**窗口**；背后的类型仍叫 `menusession`，所以 `session` 也能写，两个词指的是同一个东西。
只有要改**某一个**玩家时才需要点名窗口——哪些语法要、哪些不要，[窗口](windows.zh-CN.md)里有一张表。

## 两种模式在协议上是两回事

`phantom` 和 `static` 不是同一个东西的两种风格，而是两套机制；一个菜单用哪套，决定了物品归谁。

**`phantom`——插件自己把窗口画出来。** 它挑一个窗口编号，发一个"打开界面"包，再发一个整窗内容包；此后玩家发来的
**每一个容器点击包都被取消**，内容随后被重发回去。服务端上根本不存在对应的物品栏：玩家看到的物品住在插件自己的
内容数组里。所以格子里的东西是菜单的，玩家拿不走，"看起来拿起来的那一块"只是客户端的本地预测，会被下一个包纠正
回去。

**`static`——服务端真的建了一个。** 给玩家打开一个真实的 Bukkit 物品栏，插件改为监听 Bukkit 自己的
`InventoryClickEvent`、`InventoryDragEvent` 和 `InventoryCloseEvent`。容器格子里是真的物品，所以玩家能移动、交换、
丢弃它们，`override slot` 摆上去的家具也会被搬走。

两条会直接反映到语法上的区别：

- **下面那半场归谁。** `static` 里那 36 格就是玩家自己的背包，菜单在那里什么都没有——`setElement` 甚至会拒绝
  容器以外的格子，并给出说明。`phantom` 里，只有背包**显示**时那半场才是玩家的（窗口实时镜像他真实携带的东西）；
  隐藏之后它就是菜单自己的空间，而这正是 `player layout` 描述的东西。
- **`refresh` 在 `static` 里没事可做。** 客户端靠服务端真实物品栏自己保持同步，所以 `refresh the menu window …`
  在那边是空操作；`the cursor item` 也只在 `static` 里有值，因为 `phantom` 的点击包里根本不带物品本身。

最后一条区别写脚本时最要紧：**`phantom` 是按钮板，`static` 是真箱子。** 表格和各个开关在
[两种模式](modes.zh-CN.md)。

## 窗口是怎么画出来的，以及 `refresh` 为什么存在

打开一个窗口是两个包，顺序固定：先**打开界面**（窗口编号、布局对应的窗口类型、标题），再**整窗内容**——
按窗口槽位顺序，每格一个物品或什么都没有。

第二个包里的物品来自当前显示的那一页：页面每个映射了图标的键，都把图标放进布局给这个键的格子；`override slot`
写过的内容在之后覆盖上去。所以玩家第一眼看到的窗口就是"这一页渲染出来的样子"。这个数组的长度就是客户端窗口的长度——
先是容器格子，再是玩家那半场；同一个包要么把它填成玩家自己的物品（`phantom` 且背包显示），要么留给菜单（隐藏）。

**物品为什么会"弹回去"。** 客户端对每一次容器操作都会先在本地预测一个结果，而服务端的回答还没到。`phantom` 里
没有真实物品栏来纠正它，所以只能由插件来纠正：取消这个点击包，再把客户端弄错的那部分窗口重发一遍。

- 只会改动它自己那一格的点击：重发那一格。
- 可能在**格子之间**搬东西的点击——Shift 点击、数字键、副手交换、中键、双击收集：重发整个窗口。
- 拖拽：它扫过的每一格都重发，因为只放回一格不够。

这就是"拿起来又弹回去"的全部内容，也是 `phantom` 比 `static` 多花一点性能的地方。它发生在**点击冷却被询问之前**，
所以哪怕这次点击随后被冷却丢掉，客户端那边的预测也已经被纠正了。

**`refresh` 是干什么的。** 上面这套修补，正是脚本背着客户端改了内容之后需要的东西。`refresh the menu window …`
重发整个窗口；`refresh the slot N in …` 重发一格；`static` 里它什么都不做，因为服务端真实物品栏本来就是事实。
`set icon in slot N of {_window}` 自己就会把窗口发一遍，不用写 `refresh`：`set` 走的是 `setIcons(…, true)` 这条路。

## 为什么改标题要重新开一次窗口

**协议里没有"设置标题"这个包。** 窗口标题能变的唯一方式是**再发一次打开窗口的包**，所以"改标题"就是这么实现的：

- `phantom` 里就是再开一次：打开界面包，后面跟着整个内容，由 `TaskUtil.sync(delay = 0)` 推迟——也就是
  **下一 tick**，因为客户端会忽略"窗口刚打开那一 tick 内的标题变化"；
- `static` 里是同一件事手工做一遍：给真实容器菜单设好标题，再为它发一个全新的打开界面包，**同一 tick** 就发。

对 `phantom` 来说，一 tick 就是全部的延迟；这是客户端给的边界，不是对网络的猜测。

三件事由此而来，每一件都解释了一种脚本表现：

- **改标题会重发内容。** 因为第二个包是一次完整的打开，那一刻窗口里是什么，屏幕上就回去什么——所以标题背后
  那个内容数组是有意义的。
- **窗口关掉之后它什么也不做。** 推迟的任务会先重新检查观看者，而关闭窗口会把它清掉，所以一个还在路上的标题更新
  不可能把一个玩家已经关掉的窗口重新放回屏幕。客户端测试里正好有一条针对这个顺序的用例。
- **屏幕可能比模型晚一 tick。** `the title of {_window}` 读的是窗口自己的标题，语句执行的那一刻就变了；
  而**客户端**手里那个窗口要等第二个打开界面包到达才带上新标题。所以"同一 tick 里写标题再读回来"拿到的是新值，
  而"同一 tick 里读客户端那个窗口"拿到的还是旧标题——人工验收里"一条命令里开窗 + 改标题"查的就是这件事。

语法（`and refresh`、每页标题）在[窗口](windows.zh-CN.md)，文本与颜色写法在[标题](titles.zh-CN.md)。

## 一次点击是怎么被判定的

点击从两条完全不同的路进来，而且在脚本看到之前就已经分好类了：

- **`phantom`**：点击就是一个容器点击包。它在网络线程上被读取，用包里的*模式*、*按钮*和*槽位*翻译成插件自己的
  点击类型，然后交回主线程。插件叫不出名字的点击会被**丢掉**，而不是抛异常：它所属的窗口本来就是服务端自己画的，
  忽略它才是对的。
- **`static`**：点击就是 Bukkit 的 `InventoryClickEvent`（拖拽是 `InventoryDragEvent`），由 Bukkit 自己的点击类型
  决定。记录的格子是**原始槽位**，不是 `getSlot()`：在玩家自己那半场里，`getSlot()` 是相对"被点到的那个物品栏"
  编号的，会报出一个玩家从没碰过的容器格子——然后为它跑一次回调。

之后的事情顺序固定，而这个顺序解释了两种意外：

1. **在 `phantom` 里先修补客户端的预测**（见上一节——就算整次交互接下来要被拒绝，这一步也照跑；`static`
   里没有东西需要放回去）；
2. **询问点击冷却**。距这个玩家上一次被接受的点击不足 `click delay` 时，整次交互被**静默丢弃**：没有事件、
   没有格子回调、也没有任何提示。默认值是 `create menu` **50 毫秒**、`build a menu` **5 毫秒**；
3. **格子回调运行**，这次交互碰到的每一格跑一次（拖拽就是扫过的每一格）；
4. **`on menu interact` 触发**——在回调之后，所以在里面 `cancel event` 能拒绝这次交互，却收不回一个已经跑完的回调；
5. **最后才应用 `locked icons`**——这就是为什么在 `static` 菜单里商店的"购买"回调照常触发，而商品纹丝
   不动（`phantom` 窗口本来也搬不动它们）。

`the click type` 就是 **Skript 自己的点击类型**，用的是 Skript 的词（`left mouse button`、`number key`、
`drop key`、`swap offhand key` 等）和它的字面量；`the event-clicktype` 是同一个值。它唯一带不了的信息是
**按了哪个数字键**——九个键都报成同一个 `number key`——所以那个数字从包的按钮里读出来，作为
`the pressed number key` 给出：数字键点击时是 1 到 9，其它点击都没有值。

`cancel event` 拒绝的是**整次交互**：`static` 里取消掉 Bukkit 事件，物品就不会移动；`phantom` 里本来就没有东西
可移动，客户端看到的就是那次修补。它**不能**做的是收回一个已经跑过的格子回调；要拦住，请在回调里自己 `stop`。

**一次拖拽就是一次交互。** 它是一串点击包，相位藏在按钮里；插件把它们收集起来，在结束时一次性上报，
扫过的每一格都在 `the dragged slots` 里——而只收到一格的拖拽会被游戏当成普通点击送来。机制、三种结局和脚本
该怎么写，都在[拖拽到底是怎么工作的](dragging.zh-CN.md)。

## 所有菜单操作都必须在主线程上

菜单改的是真实物品栏和真实窗口，所以每一个菜单操作都要在服务端主线程上执行。写脚本时这条线看不见，而踩到它
的方式都很隐蔽：异步 `execute` 里再 `run task later`、别的插件的异步回调、声明成 `on … async` 的自定义事件。

插件检查的是**执行的那一刻**，不是语法：不在主线程上的调用会被**放弃**并打印一句自报家门的说明——打开、关闭、
翻页、改标题、刷新、设置列表、写窗口里的图标，各有各的说法，例如
`Menu can only be opened from the main server thread, …`。

这条检查**没有开关**，因为它拦下的调用永远不合法。整个插件也一个选项都没有：不写配置文件，启动横幅的颜色
同样是问控制台自己（`net.kyori.ansi.colorLevel`），而不是由配置决定——见[尚未支持](not-supported-yet.zh-CN.md)。

## 哪些格子属于谁

槽位号是**窗口槽位**：`0` 是容器左上角，玩家那半场紧跟在后面——先 27 格主背包，再 9 格快捷栏。两种模式口径一致，
所以布局和脚本对得上号。这半场是**推导**出来的，不是每个布局单独写的：它从容器范围之后开始，所以布局的槽位范围
少一格不会报错，而是把玩家的每一格都挪一位。（唯一的例外是 lectern：它客户端菜单只有一格、完全没有玩家那半场，
所以它的布局也不带，内容包的长度正好是客户端菜单能接受的长度。）

容器之内，页面给了图标的格子就是这一页拥有的格子——布局的键，加上 `override slot` 写过的格子。在
`static` 菜单里，`with locked icons` 保护的就是这个集合：点击、Shift 点击、数字键、副手交换、丢弃、双击
收集，都拿不走这些格子里的东西，也放不进任何东西；拖拽只要碰到其中一格，整次拖拽都被拒绝。`phantom`
里这个开关什么都不保护，因为那个窗口本来就什么都搬不动。布局**空着**的格子仍然自由，所以商店（图标属于
菜单）和背包（空格子属于玩家）是同一套机制。

下面那半场由模式和 `hide player inventory` 决定：

| | 容器下方那 36 格 |
|---|---|
| `phantom`，背包显示 | 玩家自己的物品，实时镜像 |
| `phantom`，背包隐藏 | 菜单自己的空间；`player layout` 描述它，`set icon in slot N of {_window}` 往里放东西，点它和点别的格子一样会到 |
| `static` | 玩家真实的背包；永远不属于菜单，写 player layout 只会得到一句警告、什么也不会变 |

背包显示时，页面为下面那半场摆的图标会在**窗口发出去之前被清掉**，所以它不可能出现在玩家恰好空着的格子里。
而 `set icon in slot N of {_window}` 是这个玩家自己的内容，不是菜单的家具——`locked icons` 不保护它，
"每个玩家自己的高亮"才因此可能。

`player layout` 本身在[页面](pages.zh-CN.md#player-layout)；另一半——往这些格子里写图标——在
[填充菜单](filling-menus.zh-CN.md)。

## 翻页发出去了什么

翻页不是"重画窗口"。顺序是：

1. **先检查目标页的布局**，在任何东西改变之前。布局不同的页面（箱子行数不同，或者根本是另一种容器）会带一句
   消息被拒绝，页码和内容原样不动——窗口的布局是不可变的，所以翻页不可能把物品迁进一个形状不同的窗口。
2. **`on page turn` 触发**，可以取消；事件里的 `the title` 是"即将翻到的那一页的标题"，只对这一次翻页可以改。
3. **只清掉正在离开的那一页拥有的格子**——它的布局映射了键的格子，加上 `override slot` 覆盖过的格子。其它格子
   一律不动。背包菜单因此能在翻页后保留玩家放进空格子里的东西；清空整个窗口会让"带分页的背包"根本做不出来。
4. **把目标页装进窗口**（它的图标、它的 override、它的列表）。
5. **标题不同才应用标题**，也就是上一节那个"把窗口再打开一次"的包，内容跟着一起发；标题没变时改为发一次普通的
   `refresh`。所以"不带标题的翻页"和"会改标题的翻页"在协议上不一样，`static` 也因此不再每次翻页都发两遍整个窗口。

每一页都有自己的标题，所以翻页通常连标题一起换；`turn to page 2 for player with new title "…"` 给的那个标题
**只用于这一次显示**，不会写回页面。语法和页码规则在[页面](pages.zh-CN.md)。

## 窗口什么时候消失

| 发生了什么 | 底层意味着什么 |
|---|---|
| 玩家自己关掉（ESC，或菜单里的关闭按钮） | `phantom`：一个关窗包；`static`：一个 Bukkit 关闭事件。两条路都会让窗口的关闭处理器触发 `on menu close`，然后丢掉这个窗口 |
| `close the menu …` / `close the menu window …` | 插件主动关：发出关窗包，然后丢掉这个窗口 |
| `destroy the menu …` | 正在看这个菜单的每个玩家都被关出去；菜单本身也不能再被打开或交互 |
| 玩家切到另一个菜单 | 旧菜单触发一次 `on menu close`，他也不再被算进它的 `menu viewers` |
| 玩家退出、死亡、换世界 | 先触发 `on menu close`——容器还在，脚本来得及把里面的东西存下来；然后窗口被丢弃，`static` 菜单的真实物品栏也会被**清掉**而不是留着——否则它会带着玩家的物品一直留在内存里，直到服务器关服 |
| 重载脚本（`/skript reload`） | **所有菜单都被销毁**，然后才解析新脚本 |

最后一行写脚本时必须记住：菜单持有**构建它的那个脚本的回调**，所以一个活过重载的菜单会用"已经不存在的代码"
回应下一次点击。插件因此在 Skript 的预初始化事件里销毁所有菜单，早于这一批脚本被解析；重载后的脚本会重新把
菜单建起来——这也是菜单几乎总在 `on load:` 里创建的原因。用固定 id 再建一次的菜单会销毁上一个，所以两个
永远不会同时存在。

同一个清单从脚本这一侧看是什么样，以及 `menu viewers` 的细节，在[窗口](windows.zh-CN.md)。

## 这些是怎么查出来的

三层，这一节说明哪条结论由哪一层看着。

**单元测试**钉住不需要服务端的那部分：

- `ViewLayoutTest` 把每个布局的容器格子数钉在 Bukkit 自己给这个物品栏类型的大小上，并写下两个不是
  "容器 + 36"的总数：lectern 窗口是 **1** 格，beacon 窗口是 **37** 格；
- `PhantomReceptacleTest` 钉住这一页三种操作的包形态：打开只发一个打开界面包和一个整窗包，改标题会发**第二个**
  打开界面包，关闭发关窗包——另外还有 lectern 的内容包只有它那一格，以及背包显示时页面为下半场摆的图标会被清掉；
- `ViewReceptacleTest` 钉住"关闭会清掉观看者"，而这正是"迟到的标题更新不会把窗口重新打开"的原因；
- `MenuTest` 钉住翻页会保留页面不拥有的格子里的内容、布局不兼容时在任何改动之前就被拒绝，以及 `destroyAll`
  会把所有菜单一起带走；
- `PageLockedIconsTest`、`PageAuditRegressionTest` 和 `CooldownTest` 覆盖剩下的点击规则：从图标格子里拿东西的
  每一种方式都被拒绝、碰到它的拖拽整次被拒、从玩家自己那半场 Shift 点击仍然能进空格子、一次回调只发出一个全局
  事件，以及冷却会拒绝来得太早的点击。

**真实服务端**（`./gradlew serverTest`）会启动一个真的 Paper 26.2 + Skript + PacketEvents，让插件跑一串脚本：
每个元素都能注册、每个脚本都能解析、一批行为脚本里的原版 `assert` 都成立，以及日志形态正确（运行期消息走运行期
通道，没有 `Severe Error`，没有以前属于 bug 的解析形状）。每个 `@Examples` 也会在那里被解析，所以 Skript 读不了的
文档示例会直接让构建失败。

**真实客户端**（`./gradlew clientTest`）驱动一个真的 Minecraft 客户端，让它把自己收到的窗口读回来：标题、类型，
以及每个已知格子里物品的**类型**和名字。它断言翻页之后的窗口（第二个打开界面包就是在这里被端到端跑一遍的）、
下半场属于页面而不是玩家、lectern 的一格窗口和 beacon 的 1 + 36、dropper 的九格三列布局、bot 用原始包发出的
拖拽，以及"同一 tick 里改标题再关闭的窗口不会回来"。客户端是 26.1 客户端，后面挂着 ViaVersion + ViaBackwards，
所以这一层证明的是"本插件发的包能穿过真实翻译层到达真实客户端"——这条边界在
[尚未支持](not-supported-yet.zh-CN.md)里写得很清楚。

**人工验收**（`docs/manual-acceptance.zh-CN.md`）是只有坐在真实 26.2 客户端前的人才能定的部分，而这一页上的三个
机制正好都需要它：

- **lectern 的一格窗口**（`/acctype lectern`）：窗口确实是客户端为那个方块画的那一个，以及格子数写错时整个
  玩家背包都会跟着挪位；
- **重新打开之后标题有没有到**（`/acc sametick`：一条命令里开窗并改标题）：自动化断言的是读回来的值，人要确认
  屏幕上真的显示了它；
- **拖拽的各个相位**（`/acc drag`）：客户端测试发的是"手上有物品"的真实拖拽包，人工这边补上空光标，以及
  "每一格最后落在哪里""被拒绝的拖拽留下了什么"这种人眼才能确认的事。

自动化故意没覆盖的部分也写在那里：只存在于客户端的"幽灵物品"，以及两个客户端同时看一个菜单
（客户端测试只有一个 bot）。
